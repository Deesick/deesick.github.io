## 1. Executive summary

In November 2026, a phishing kit branded as the online invitation service [Evite](https://evite.com) was recovered from a client's cPanel hosting account. The intruder reportedly installed it about a week after obtaining the client's account credentials through a ClickFix attack in a separate incident. The kit consists of a PHP backend driving a compiled Vue single-page application. It presents an Evite-branded login page (Figure 1), deliberately rejects the first correct password submission (Figure 4) to prompt the victim to enter it again, and then displays a fake SMS verification prompt (Figure 6) before redirecting the victim to the genuine evite.com website (Figure 7).

The kit is assembled almost entirely from existing code. Its components include a modified GPL-licensed bot trap, an AES encryption layer derived from a banking-fraud panel, and a frontend containing remnants of DocuSign- and Microsoft-themed interfaces beneath the Evite branding. Its operator console also lacks authentication at the API layer (Figure 9). The backend contains card and identity collection handlers, but the supplied frontend provides no corresponding forms or functionality through which victims could access them.

Based on its demonstrated capabilities, the kit scores **2.95 out of 5** under the assessment framework described in §12. The score reflects a competent commodity credential phisher with weak operational security. In the analysis below, I demonstrate how the kit collects synthetic credentials during a controlled local run and delivers them to a Telegram message thread under my control (Figure 10). This establishes that credential collection and exfiltration work under the tested conditions, not that an account was compromised. No successful account takeover is demonstrated in this paper. Nor is there evidence that the kit captured credentials from a real victim: the export process removed the runtime data, and the hosting account was subsequently decommissioned.

## 2. Introduction and research scope

This is an independent technical investigation of a single artefact. It was not commissioned by the affected client, no victim data was handled, and no attacker-controlled infrastructure was contacted. The test did, however, reach public third-party services. Section 9.1 accounts for each of these connections. The objective was to understand the kit's architecture, data flow and detection surface, and to produce findings that an examiner or hosting provider could act on.

The investigation covers static analysis of the archive, one controlled loopback execution using synthetic credentials, and the detection and scoring work presented in the following sections. Figures 1–10 come either from that execution or from the extracted source. None is a capture of the live deployment. The investigation did not involve contacting the kit's original Telegram endpoint, testing any third-party service beyond the connections documented in §9.1, or attempting to attribute the activity to an individual or group.

The provenance of the findings is deliberately separated. The file set, hashes and observed behaviour are artefactual and reproducible from the sample. The intrusion narrative, including the ClickFix credential theft, the reported one-week gap and the subsequent installation of the kit, comes from the site owner. None of these details is independently established by the files. They are included to explain the reported deployment context, not presented as findings derived from the artefact.

> Hashes, file layout and observed behaviour are reproducible from the sample itself.
{: .prompt-info }

Two constraints shaped the analysis. First, the panel was exported as a ZIP archive, and the export process stripped its runtime state. The operator's configuration database is therefore absent. Second, the hosting account was subsequently decommissioned, leaving no access logs to establish whether the kit ever served a visitor. This paper consequently describes the kit and its demonstrated capabilities, not the scope or success of a campaign.

The archive is small and relatively easy to navigate. It contains 52 PHP files, 16 frontend assets, a vendored CrawlerDetect tree, a Composer vendor directory and several `.dat` state files. Its absence means the archive either predates deployment or was stripped of runtime data during export. ## 4. Kit architecture

The request path is short and conventional for a PHP application running on shared hosting.

```text
.htaccess ──▶ index.php ──▶ config.php                     (operator settings from SQLite)
                        ├─▶ includes/functions.php          (session, geo, UA, reporting)
                        └─▶ REBOOT_Firewall/index.php      (bot gate)

index.php routes:
   /api/*     ──▶ obfuscation interceptor ──▶ api/index.php      (operator console)
   /backend*  ──▶ obfuscation interceptor ──▶ backend/index.php  (capture handlers)
   everything else ──▶ SPA shell
```

The include order is central to the design. The gate loads before the application routes requests, allowing it to filter visitors before the application serves the relevant content.

```php
// index.php:15-17
require_once(dirname(__FILE__) . '/config.php');
require_once(dirname(__FILE__) . '/includes/functions.php');
include_once(dirname(__FILE__) . '/REBOOT_Firewall/index.php');
```

Configuration is stored in a single-row SQLite table and edited through the operator console. The capture sequence is controlled by an operator-defined `flow` array rather than hardcoded application logic. As a result, two deployments using identical source code could present different sequences to visitors.

The gate is a modified version of **Blackhole for Bad Bots**, a GPLv2 plugin by Jeff Starr, version 4.1. The upstream plugin traps crawlers that ignore `robots.txt`. This fork adds several features relevant to the phishing flow: `href.li` wrapping for redirects, country and device-type restrictions, a `completed.dat` re-visit ban, and a `/config` exemption for operator IP addresses marked with `- C`.

## 5. Technology stack

|Layer|Confirmed technology|
|---|---|
|Hosting|Apache/cPanel, PHP 8.x|
|Backend|Plain PHP with `SQLite3`|
|Frontend|Vue 3 compiled with Vite, hashed chunks|
|Gate|Blackhole for Bad Bots (GPLv2), modified|
|Configuration|Single-row SQLite table and JSON schema|
|Transport|AES-256-GCM via OpenSSL and WebCrypto|
|Exfiltration|Telegram Bot API and PHP `mail()`|
|Redirect laundering|href.li|
|Geolocation|ip-api.com over plaintext HTTP|

Three implementation choices explain much of the kit's design. PHP on cPanel requires no separate application server or database service, making the application relatively easy to deploy in a typical `public_html` directory. The compiled Vue frontend separates the presentation layer from the PHP backend, allowing the branding to be changed by replacing the build assets. The use of Telegram also removes the need for the operator to maintain a dedicated collection server. The operator's chat effectively serves as the collection endpoint.

The technologies in the table are confirmed by the source code. The explanations above are interpretations of why those choices may have been made, rather than evidence of the operator's intent. Two absences are also worth noting: the kit uses SQLite rather than a separate database server, and it has no custom collection backend. Captured data is sent directly to Telegram or through PHP's mail functionality.

### 6.2 The gate: cloaking rather than blocking

The gate is one of the kit's more effective operational components. It matches search-engine user agents against a regular expression and treats matching requests as safe. These requests are not logged by the relevant branch.

```php
// REBOOT_Firewall/index.php:208-213
function blackhole_whitelist($ua)
{

    if (preg_match("/(aolbuild|baidu|bingbot|bingpreview|msnbot|duckduckgo|adsbot-google|googlebot|mediapartners-google|teoma|slurp|yandex)/i", $ua)) {
        return true;
    }
```

A visitor classified as a bot is not simply shown an access-denied response. Instead, the gate returns an empty page containing a script that redirects the browser to the configured exit link.

```php
// REBOOT_Firewall/index.php:149-156
    if ($badbot > 0) {

        blackhole_delete_all_sessions();

        echo "<script>top.location.href = '{$exit_link}';</script>";

        exit;
```

Combined with the `href.li` wrapper applied to redirects, this behaviour sends matching crawlers and other visitors classified as bots to the genuine brand website, while visitors who pass the checks are served the phishing interface. This is cloaking rather than conventional blocking. It also illustrates why a scanner reaching the genuine brand site cannot, by itself, establish that the underlying URL is benign.

### 6.3 The capture sequence

The kit uses a three-stage capture sequence, which was confirmed during the controlled run. The first credential submission is collected and forwarded before the application deliberately rejects it.

```php
// backend/index.php:262-275
            if ($dual_login) {
                // Check if this is the first login (repeat not set) or second login (repeat is true)
                $isFirstLogin = !$isRepeat;

                if ($isFirstLogin) {
                    // First login: redirect to login again with error flag
                    error_log("dual_login is true, rerouting to login again (first login, repeat=" . var_export($repeat, true) . ")");
                    handleRedirection($type, 1);
                } else {
                    // Second login: show OTP and proceed normally
                    error_log("dual_login is true, second login completed (repeat=" . var_export($repeat, true) . ")");
                    $_SESSION['display_otp'] = true;
                    handleRedirection($type, 0);
                }
```

The visitor sees what appears to be an ordinary credential error (Figure 4) and is prompted to enter the credentials again. The backend records both submissions separately:

```php
// backend/index.php:233-238
            $message .= "----- {$page_name} Info | Reboot Inc -----\n";
            $message .= ($dual_login && $isRepeat ? "Second Username" : "First Username") . "\t\t: " . $username . "\n";
```

### 6.4 Handlers that exist but are not exposed by the frontend

The backend also implements mailbox (`email`), card and identity stages. The card handler accepts payment details, including a PIN, and constructs a message for exfiltration:

> The card handler is implemented and wired to exfiltration, but no route or form in the supplied
> frontend reaches it. It demonstrates what the backend can do, not that card data was collected.

This code is present and connected to the exfiltration logic, so it is relevant to the kit's overall capability. It is equally important, however, to distinguish backend functionality from what the supplied frontend exposes to a visitor.

The shipped frontend registers routes for `/`, `/login`, `/twofa`, `/config`, `/incomplete-setup` and the error pages. It does not call `addRoute`, so the configuration cannot inject additional pages at runtime. The card-submission helper is referenced only by an embedded self-test that submits demonstration values. A redirect to `/card` or `/info` therefore falls through to the catch-all route rather than displaying a corresponding form.

The distinction is that the backend contains card and identity handlers, but the supplied frontend does not provide a victim-facing route or form for either stage. The handlers may still be addressable through direct requests to the backend, depending on the request structure and server-side checks. The analysis does not establish that a victim could reach them through the normal interface in this build. This distinction matters to the assessment in §12, which does not treat the sample as a functioning card-phishing frontend.

### 6.5 The operator console

`api/index.php` dispatches requests by method and path. Across its 1,084 lines, there is no apparent session check, token check or capability test protecting the configuration endpoints. The word `Authorization` appears once, in a CORS header. Reading the configuration requires no prior authentication:

```php
// api/index.php:921-950
    case 'GET /api/config':
    case 'GET /config':
        try {
            $requestedKey = isset($_GET['key']) ? trim($_GET['key']) : '';

            if ($requestedKey !== '') {
                $value = $configDB->getConfigValue($requestedKey);
                if ($value === null) {
                    http_response_code(404);
                    echo json_encode([
                        'success' => false,
                        'error' => "Configuration key '$requestedKey' not found"
                    ]);
                    break;
                }

                echo json_encode([
                    'success' => true,
                    'key' => $requestedKey,
                    'config' => $value,
                    'timestamp' => date('c')
                ]);
            } else {
                $config = $configDB->getAllConfig();
                echo json_encode([
                    'success' => true,
                    'config' => $config,
                    'timestamp' => date('c')
                ]);
            }
```

The console page itself asks for a password (Figure 8), but the API does not enforce the same requirement. The `/config` route is explicitly exempt from the frontend's navigation guards, while `/login` and `/twofa` are not. More importantly, the server does not re-check the session when handling the configuration request.

`POST /api/config/login` verifies the supplied password and then appends the caller's address to `whitelist.dat` with a `- C` flag, allowing the gate to exempt that address. In practice, the login operation grants the caller an exemption from the gate; it does not provide effective authentication for the API. The gate is a filtering component, not an access-control mechanism.

## 7. Credential collection and data flow

Figure 10 provides the clearest runtime evidence of the collection process. It shows the receiving end of the flow: three messages from a single session, each carrying the kit's vendor header and arriving in the order in which the corresponding values were submitted.

![Chat thread of three capture messages from one session, with password and OTP values covered by grey bars]({{ 'assets/img/posts/evite-kit/fig10-telegram-capture-thread-redacted.webp' | relative_url }})

_Figure 10. Three messages captured during one session, in submission order, each carrying the kit's vendor header. The Telegram thread is researcher-controlled. Password and OTP values are covered; the headers and remaining metadata are unaltered._

The messages also confirm two details visible only during execution. The header is hardcoded as `---- Evite Info | Reboot Inc ----`: the page name is operator-controlled, but the vendor string is not. Each message also includes the client IP address, city, state, device type, operating system and browser. This explains why the kit performs a geolocation lookup when generating each report.

|Destination|Mechanism|Content|
|---|---|---|
|Telegram|Bot API `sendMessage`, POST JSON, HTML parse mode|Captured fields, IP metadata, city, state, device, OS and browser|
|E-mail|PHP `mail()`, From: `"Log Messanger "`|Similar capture data, with an ip2location demo link|
|Telegram visitor notification|`file_get_contents` GET to `sendmessage`|First-visit notification containing IP, country, user agent, ISP and link|
|`REBOOT_Firewall/completed.dat`|Append|IP, method, protocol, date and user agent, used for the re-visit ban|
|`REBOOT_Firewall/bots.dat`|Append|Similar request metadata for blocked crawlers|
|`REBOOT_Firewall/whitelist.dat`|Append on console login|IP address with a `- C` flag|
|`includes/debug.log`, `api/debug.log`, `includes/obfuscation-debug.log`|Append|Request arrays, step decisions, device UUIDs and response structures|

One important detail is what the kit does not store locally. Captured values are not written to the database. The `config.db` file holds configuration, while `completed.dat` records an address and user agent for the re-visit restriction. There is no dedicated victim-data store on the host. For an examiner, this changes the likely location of the evidence: acquiring the server may recover configuration and telemetry, but not necessarily the credentials collected by the kit. Those records are sent to the operator's chat or mailbox.

Three capabilities need to be distinguished.

First, the **card handler is implemented and connected to the exfiltration path**. If it receives the required card fields, it constructs a message and forwards it through Telegram or e-mail, as the source excerpt shows.

Second, the **identity handler constructs and sends a message containing a name, address, SSN and date of birth** through the same exfiltration path. It then attempts a second POST to a helper at `http://localhost:3000/send_results`. That call appears defective: the request object is not populated beyond a session identifier. The defect affects the optional auto-login integration, not the Telegram or mail delivery that occurs beforehand.

Third, **neither handler is exposed through a corresponding form in the supplied frontend** (§6.4). The backend therefore contains these collection capabilities, but the normal victim-facing flow does not provide a route to trigger them. Nothing in this investigation establishes that card details, SSNs or dates of birth were collected from a victim.

## 8. Obfuscation and evasion

The `obfuscator/` directory appears, at first glance, to be the kit's most sophisticated component. Closer inspection suggests otherwise.

The implementation uses AES-256-GCM with a 12-byte random IV and a 16-byte authentication tag. The tag is verified during decryption, and the payload is serialised as `base64(IV || ciphertext || tag)`, with `+/=` remapped to `-_.`. The cryptographic primitive is implemented correctly. The weakness lies in how the key is derived:

```php
// obfuscator/obfuscate.php:27-37
    public function deriveKey($deviceUUID, $purpose = 'req') {
        try {
            // Create password from device UUID
            $ctx = strtoupper($purpose ?: 'req'); // REQ or RES
            $password = ($deviceUUID ?: 'default-device-uuid') . 'ATS_SECRET_SALT_2024:' . $ctx;
            
            // Derive key using PBKDF2 (same parameters as extension)
            $salt = 'ATS_KEY_DERIVATION_SALT:' . $ctx;
            $key = hash_pbkdf2('sha256', $password, $salt, 100000, $this->keyLength, true);
            
            return $key;
```

The device UUID is the only variable input that contributes secrecy to the derivation, but the client generates it and sends it in a clear request header. The salts, purpose labels, IV placement and envelope keys are also present in the client bundle. An observer with access to the client bundle and the transmitted UUID can reproduce the key derivation and decrypt traffic in either direction. The layer therefore provides no meaningful confidentiality against an observer with those materials. Its practical effect is to make body inspection and signature-based scanning less straightforward.

The implementation also includes a switch that disables the layer:

```php
// obfuscator/obfuscation-middleware.php:34-40
            // Check for debug mode
            $debug = isset($_SERVER['HTTP_X_DEBUG']) && $_SERVER['HTTP_X_DEBUG'] === 'true';
            if ($debug) {
                // Store in global for response middleware
                $GLOBALS['_obfuscation_debug'] = true;
                return ['success' => true, 'error' => null, 'deviceUUID' => null];
            }
```

Setting the `X-Debug: true` request header bypasses the obfuscation layer in both directions. No credential or prior session state is required. The code appears to be a debugging convenience left in the production path; the available evidence does not establish why it was retained.

Three further observations are relevant to the kit's evasion and operational security.

**Donor code as noise.** The endpoint map includes routes such as `/device/verify-totp` and `/device/dashboard-screenshot`, while the field map includes names such as `balanceText` and `documentNumber`. None of these routes or fields is used by this kit. The obfuscation layer appears to have been transplanted from an Automated Transfer System (ATS), or banking-session stealer, protocol. Its salts retain the `ATS_…2024` labels. The unused code adds no functionality to the observed flow and can mislead analysis based on string searches alone.

**Dead configuration.** A hardcoded IP-geolocation API key appears in `config.php`, but the code does not use it. Geolocation instead relies on the keyless ip-api.com service. Two e-mail validation functions also have no call sites. One opens SMTP connections to a victim's MX servers and issues `RCPT TO` commands. The code therefore contains the capability to probe mail servers, but the investigation found no evidence that this functionality is invoked.

**Logging that helps defenders.** The interceptor appends to `includes/obfuscation-debug.log` on every call, without an apparent debug-mode check. The log records request keys, device UUIDs and decoded response structures. If preserved from a compromised host, it could help establish activity and correlate sessions.

The kit does not appear to implement sandbox or virtual-machine detection, a time-based trigger, server-side anti-debugging or environment fingerprinting beyond device type and country. Its evasion is primarily social and network-based: cloaking, referrer hiding and a plausible credential-rejection message.

## 9. Dynamic analysis

The kit was executed once on loopback using synthetic credentials. The original Telegram configuration was replaced with a researcher-owned bot, so the capture messages were delivered to a controlled account rather than the operator's chat. The test was not performed inside a snapshot-recoverable, network-isolated virtual machine, as the methodology would ideally require. That deviation is documented in §14.

The server log provides the clearest record of the sequence. The screenshots show selected points in the flow; the log timestamps the underlying branch decisions.

```text
[09:14:54] Processing POST with type: login
[09:14:54] DEBUG repeat value: false (type: boolean)
[09:14:56] dual_login is true, rerouting to login again (first login, repeat=false)
[09:14:56] showTwofa: 1
[09:14:56] going to twofa: 1
[09:15:23] Processing POST with type: login
[09:15:23] DEBUG repeat value: true (type: boolean)
[09:15:29] dual_login is true, second login completed (repeat=true)
[09:16:32] Processing POST with type: twofa
[09:16:34] going to exit link: https://href.li?https://evite.com/
[09:16:34] Obfuscation result type: array, encoded length: 337
```

Four details are relevant. The `repeat` value arrives as a boolean, confirming that the dual-login branch is not the result of an unexpected type conversion. The 29-second interval between the two login submissions is consistent with a user reading the rejection message and re-entering the credentials, although the timing alone cannot establish what a real victim would do. The responses pass through the obfuscation interceptor, and the complete sequence takes approximately 100 seconds.

The run directly demonstrated the page load, provider overlay, rejection, second submission, countdown, code prompt and exit redirect (Figures 1–7). It also produced three capture messages in a researcher-controlled Telegram thread (Figure 10) and an unauthenticated configuration response (Figure 9). ## 10. Infrastructure and indicators

The kit relies on very little infrastructure of its own. The operator needs a Telegram bot and access to a compromised hosting account, but no dedicated collection server. The Evite branding and favicon CDN path are presentation elements that can be changed easily, so they are not included as indicators.

|Indicator|Type|Durability|
|---|---|---|
|`Reboot Inc` in exfiltration message templates (Figure 10)|Kit string|Likely to persist until the vendor string is changed; high specificity|
|`/api/health` returning `"service":"Vue Config Dashboard API"`|HTTP response|Specific to this generation, but easy to change|

## 11. Detection opportunities

The YARA rule targets the sample through four independent sets of strings: the vendor name and field vocabulary, the GCM implementation and its envelope keys, the Evite frontend, and the modified gate. The latter differs from upstream Blackhole through features such as `href.li` wrapping and the `completed.dat` re-visit restriction.

```yara
rule Reboot_Evite_Phishing_Kit {
    strings:
        $vendor   = "Reboot Inc" ascii
        $f_reuid  = "reuid" ascii          /* further field strings omitted here */
        $f_reps   = "reps" ascii
        $f_reotp  = "reotp" ascii
        $aes      = "aes-256-gcm" ascii
        $env      = "mjpq8e9z" ascii
        $envhash  = "k3r2s1t0" ascii
        $href     = "href.li?" ascii
        $loggedat = "completed.dat" ascii
        $evite1   = "Evite: Online Invitations" ascii
        $evite2   = "g0.evitecdn.com" ascii
        $blackhole = "Blackhole for Bad Bots" ascii
    condition:
        filesize < 6MB and
        (
            ( $vendor and 2 of ($f_*) )
            or ( $aes and $env and $envhash )
            or ( $evite1 and $evite2 )
            or ( $blackhole and $href and $loggedat )
        )
}
```

Using the complete string set in the rule file, the conditions matched four files in the extracted tree:

```text
index.php
backend/index.php
REBOOT_Firewall/index.php
obfuscator/obfuscate.php
```

The listing above is abridged: `$f_reem`, `$f_recn` and `$f_renm` are omitted for length, but the condition is unchanged. Both rules compiled under libyara 4.5.4, the engine behind the `yara` CLI, accessed here through the official `yara-python` bindings. They were run against all 99 extracted files. The kit rule matched the four files listed above; the donor rule matched only `obfuscator/obfuscate.php`.

An earlier logic-emulation pass identified two defects in the draft rule: an endianness error in a file-header test and an initial condition that was too narrow to match the shell or obfuscator. Those issues were corrected before the rules were compiled and tested.

Network-side detection may be more useful than brand-based matching:

- A web server initiating outbound Telegram Bot API traffic, particularly where the application has no legitimate reason to use Telegram.
    
- A `GET /api/config` request returning operator configuration in the response body. This is useful only where the monitoring system records response bodies.
    
- Repeated login POST requests from the same source, followed by a two-factor authentication route. This matches the sequence observed in the §9 log.
    
- An `href.li` redirect originating from a login page. The pattern is weak on its own but more useful when correlated with credential-submission behaviour.
    

Several approaches are less reliable. Matching Evite branding or page text is unlikely to remain effective because the frontend skin can be replaced. Matching `/twofa` alone is also too generic to identify this kit. Card-field matching is similarly weak for this build because the supplied frontend does not expose a card form.

## 12. Threat assessment and scoring

The six dimensions and their weights were established before assigning values and applied consistently to this sample.

The weights are as follows: credential theft 25%, exfiltration 15%, evasion 20%, operational sophistication 20%, targeting and impact 10%, and detectability 10%. Detectability is scored in the opposite direction: a score of 5 means the kit is trivially detectable. Its contribution is therefore inverted using `10 × (6 − score)`.

```text
(25·cred + 15·exfil + 20·evas + 20·soph + 10·impact + 10·(6−detect)) / 100
```

|Dimension|Score|Basis|
|---|---|---|
|Credential theft|4|Three-stage capture confirmed during execution (Figures 4–6 and 10); no cookie or token theft demonstrated|
|Exfiltration|3|Telegram and mail delivery implemented; Telegram delivery confirmed in the controlled run (Figure 10); no local victim-data store; helper path defective|
|Evasion|3|Cloaking works (§6.2); the AES layer provides no meaningful confidentiality (§8); a debug header disables it|
|Sophistication|2|Donor code, no evident test suite, several implementation defects and an unauthenticated console (§6.5)|
|Targeting / impact|3|Mailbox credentials and a one-time code are collected; these could support account takeover, but no takeover was demonstrated. Card and identity stages are not exposed by the frontend (§6.4)|
|Detectability|4 → 2|The kit exposes its configuration (Figure 9) and a service banner|
|**Composite**|**2.95 / 5**||

The sensitivity calculations show how the result changes under different assumptions:

|Scenario|Cred|Exfil|Evasion|Soph.|Impact|Detectability (adjusted)|Composite|
|---|---|---|---|---|---|---|---|
|As analysed|4|3|3|2|3|2|(100+45+60+40+30+20)/100 = **2.95**|
|Card and identity frontends existed and were reachable|5|3|3|2|4|2|(125+45+60+40+40+20)/100 = **3.30**|
|A victim were proven|4|3|3|2|4|3|(100+45+60+40+40+30)/100 = **3.15**|
|Obfuscator rebuilt with a server-side key and no debug bypass|4|3|4|2|3|2|(100+45+80+40+30+20)/100 = **3.15**|

The victim scenario scores 3.15 because evidence of a victim would increase the impact assessment, but would not by itself establish a successful compromise. Demonstrating an account takeover would be a different finding and would require separate evidence. The score also rises by a similar amount when the obfuscation is strengthened, although the change in demonstrated impact remains more consequential to the overall assessment. These scenarios are sensitivity tests, not confidence intervals.

Confidence is not uniform across the dimensions. The capability scores are supported by source analysis and a reproducible local run, so confidence in them is high. The impact score relies partly on the potential consequences of collecting credentials and a one-time code, so confidence is lower. The composite should be read with that distinction in mind.

## 13. Defensive recommendations

For hosting providers and site owners:

- Treat the discovery of a PHP phishing kit in a web root as an account compromise, not merely a file-upload incident. The site owner reports that credentials were stolen through a ClickFix page about a week before the files appeared. If that account is accurate, the attacker had working panel access before deploying the kit. Rotate every credential the account could access, including mailbox credentials and those for linked DNS or CDN services.
    
- Preserve and examine the kit's logs before removing the files. Relevant locations include `includes/obfuscation-debug.log`, `includes/debug.log`, `api/debug.log` and the `.dat` files under `REBOOT_Firewall/`. They may be the only remaining local record of activity. Do not assume captured data will be present on the server: the kit sends it to an operator-controlled chat or mailbox. The response should therefore include notification and credential resets, not just file recovery.
    
- Monitor for `href.li` in redirect chains and outbound Telegram traffic originating from web hosts. Both are relatively straightforward to detect and are relevant to this sample.
    

For defenders more generally:

- Do not treat familiar branding as evidence that a page is legitimate. Cloaking can cause scanners and human visitors to receive different content. A page displaying the genuine brand is not, by itself, evidence of benign behaviour.
    
- Treat a login flow that rejects a submission and then prompts for the same credentials again as a potential collection technique, particularly when followed by a code-entry prompt. Correlating those events can help identify this behaviour regardless of the frontend branding.

## 14. Limitations

- **No evidence from the live host.** The export process stripped runtime data, and the hosting account was subsequently decommissioned. There is no access log, populated `config.db` or evidence establishing that a visitor interacted with the deployed kit. Claims about deployment activity, victim volume or operator identity cannot be made from the available material. Every figure in this article comes from the local test build or the extracted source, not the compromised host.
    
- **No account takeover was demonstrated.** The investigation shows credentials and a one-time code being collected and forwarded. It does not demonstrate a successful mailbox login, an MFA bypass or that the collected code was still valid when submitted. These are possible consequences, not findings.
    
- **The entry-vector timeline is based on the site owner's account.** The reported ClickFix credential theft and the one-week interval are not independently verified. No artefact dates the intrusion, corroborates the reported vector or establishes a direct link between the kit and the account compromise.
    
- **Dynamic analysis was not performed in an isolated virtual machine.** Execution took place on loopback using synthetic data and a researcher-owned Telegram bot. The test nevertheless reached the public services listed in §9.1. The observed behaviour is genuine, but the containment was weaker than the methodology ideally requires.
    
- **Card and identity stages are implemented capabilities, not demonstrated victim-facing behaviour.** The handlers are present in the backend and connected to the exfiltration logic, but the supplied frontend does not expose corresponding forms (§6.4). No figure in this article shows a card or identity form because neither is present in the tested build.
    
- **The detection rules were compiled and tested against the sample, but have not been validated against a broader corpus.** They matched the expected files in the extracted tree. Their effectiveness against modified samples and benign software remains untested. They should therefore be treated as sample-specific detection rules, not as a complete detection solution.
    
- **The investigation covers one sample.** The findings do not establish prevalence, the behaviour of the vendor's other products or the identity of its customers. Donor-code findings indicate code reuse across families, not who reused which component. `Reboot Inc` is a string chosen by the kit's author and may assist sample clustering, but it does not establish an identity.

## 15. Conclusion

This kit is a useful counter-example to the assumption that obfuscation implies sophistication. Its most elaborate component is a transplanted cryptographic layer that provides no meaningful confidentiality (§8), can be bypassed with a single request header and is integrated into an application whose operator console exposes configuration without API-level authentication (§6.5). Its most effective component is a long-standing, publicly available GPL bot trap, modified to show crawlers a different destination from the one presented to visitors (§6.2).

The kit performs its core credential-theft flow competently. It captures credentials in three stages (Figures 4–6), deliberately rejects the first submission, introduces a configurable verification delay, forwards the collected values to a Telegram chat (Figure 10) and redirects the visitor to the genuine service (Figure 7). The collected credentials and one-time code could support account takeover if they were valid and used within the code's validity period. Neither a successful login nor an MFA bypass was demonstrated in this investigation.

The absence of card and identity forms in the supplied frontend is an important distinction. The backend nevertheless contains handlers and exfiltration logic for card numbers, CVVs, PINs, SSNs and dates of birth (§6.4). A related build exposing those stages would present a materially different risk. Anyone assessing another deployment should therefore inspect both the backend handlers and the frontend routes before assuming that the limitations observed in this sample apply to the wider kit.
